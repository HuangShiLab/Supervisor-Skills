# Binary delivery review

## Rule

A deliverable is ready only when every mandatory item answers `yes`. Do not use
"mostly", "probably", or "will fix later" for a mandatory item. If any item
fails, label the output as draft and state the failed IDs.

## Scope and goal

1. Does the delivery satisfy the ledger goal, not merely one step?
2. Is every delivered artifact linked to a ledger task?
3. Are all substitutions, deferrals, and scope changes explicit?
4. Is every planned dependency represented or explicitly deferred?

## Evidence and correctness

5. Does every conclusion have a current source artifact?
6. Do the text, figure, table, and source data contain the same numbers and units?
7. Are denominators, populations, and exclusions stated?
8. Is uncertainty appropriate to the experimental design?
9. Is a contrary or weak result reported rather than omitted?

## Artifact integrity

10. Do all promised files exist at their stated paths?
11. Are temporary, duplicate, and superseded outputs excluded from the deliverable?
12. Are file names, figure numbers, table numbers, and section references current?
13. Do rendered figures contain every panel cited by the caption?
14. Do rendered tables and references resolve?

## Reproducibility

15. Can the release checks run from the recorded state?
16. Are software versions, parameters, seeds, inputs, and checksums recorded?
17. Are raw and derived data either available or covered by a concrete access statement?
18. Are outputs deterministic except where nondeterminism is documented?

## Reviewer and user requests

19. Is every reviewer comment numbered with a disposition?
20. Are accepted and rejected tracked changes explicitly distinguished?
21. Have prior criticisms relevant to this deliverable been checked?
22. Are unresolved issues listed rather than omitted?

## Failure report

If delivery fails, report:

1. failed checklist IDs;
2. affected artifacts;
3. whether the output is a draft or blocked;
4. the minimum repair path;
5. whether user input is required.
